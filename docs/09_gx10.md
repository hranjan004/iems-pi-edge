# The ASUS Ascent GX10 target

The setup guide is `gx10/README.md`. This document records what the GX10 target
changed in the repository and why, so a later reader can tell which files are
shared with Pat's box and which are GX10 only.

## Shape of the target

One GX10 runs every service. Pat's box is used only before the event, as the
source of the training data and of the deployed models. At the event the box
needs no network.

| concern | Pat's box | GX10 |
|---|---|---|
| live data | eGauge and Solar Assistant producers | `gx10/replay/replay_producer.py` replaying Pat's recorded data |
| AnyLog | `anylogco/anylog-network:2.1.2608`, amd64 | `anylogco/anylog-network:local-nuitka-arm`, loaded from `AnyLog-latest-arm.tar` |
| training | Mac CPU, models shipped by `deploy_rolling.sh` | GB10 GPU in `nvcr.io/nvidia/pytorch:25.09-py3` |
| inference | ONNX Runtime, x86 CPU | ONNX Runtime, Grace CPU (unchanged code) |
| LLM | qwen2.5 in Ollama, CPU | Nemotron 3.5 Lightning on the GB10, Ollama API |
| compose | `docker-compose.yaml` at the deployment root | `gx10/docker-compose.gx10.yaml`, project `microgrid-gx10` |

## Shared code that changed

| file | change |
|---|---|
| `services/iems/training/train_rolling.py` | runs on CUDA when available (`DEVICE`, `BATCH` env). Tensors move to the device in `unpack`, predictions come back with `.cpu()`, the checkpoint is saved as CPU tensors so `export_physical.py` loads it unchanged. Seed, folds and the default batch of 256 are as before |
| `services/iems/training/export_physical.py` | folds any external tensor file back into the `.onnx`. The dynamo exporter in newer torch (the NGC images) writes weights to a side `.onnx.data` file, which the image build and the md5 deploy check would silently drop |
| `services/iems/backend/Dockerfile` | `ARG BASE_IMAGE` so the GX10 can build FROM its own inference image. The default is still `microgrid-ucsc-dev_fin-iems-inference`, so Pat's build is unaffected. The site files it copies (`appliance_data_updated.txt`, `breaker_ratings.yaml`) now sit beside it, as they do in `~microgrid/iems-backend-build` |
| `docs/04_training_pipeline.md` | the run sequence no longer calls `gen_norm_physical.py` after `train_rolling.py`, which would have replaced the 18 feature norm with a 14 feature one |

The root `docker-compose.yaml` is unchanged. It stays the Mac and Pat's box
definition, and the GX10 has its own file so neither can break the other.

## The data export

`gx10/scripts/pat_export_remote.sh` reads the monthly partitions of
`egauge_kafka` (from 2026-08-18) or `energy_readings` (from 2026-08-01) one day at
a time through the `ts` index, under `nice`. The 6 s grid uses the same rule as
`feature_builder._resample_uniform`, the last reading at or before each grid
point, so the training windows match what the runtime builds. On Pat's box a day
took 10 to 60 s and produced about 1 MB of gzip.

The 2026-10-10 export holds 70 days of 6 s data (2026-08-01 to 2026-10-09), raw
1 s data for 2026-10-07 to 2026-10-09, 976,788 Solar Assistant rows, and the six
deployed model files.

## Observed on Pat's box during the export

## Nemotron NILM engine, 2026-10-11

Nemotron 3.5 Lightning 30B-A3B (BF16, LoRA r16) replaces the BiLSTM as the live
appliance engine, with the retrained BiLSTM per panel as per-head fallback and
as the distillation teacher. Round 2 (400 LoRA steps) is deployed: held-out
agreement with the gated teacher 0.9191 (round 1 0.8214); Panel 1 0.938, Panel 2
0.945, Panel 3 0.906. Details, per-head numbers and the deploy procedure are in
gx10/README.md, section "Nemotron as the NILM engine".

Fixes found on the way: the restored LR scheduler overrode the config
(`override_opt_param_scheduler`), the merge left a root-owned model the host
could not replace (now swapped inside the container), and a long-running
training container can lose the GPU after a host systemd reload (`docker
restart nilm` restores it).

## Operating the GX10 (2026-10-11)

**Live source.** The authenticated web collectors (`iems-web-collector`, user systemd) are the live source. The replay producer sits behind the Compose profile `replay` and its restart policy is `no`. Start it only for a demo, and only with the collectors stopped:

```bash
docker compose -f gx10/docker-compose.gx10.yaml --profile replay up -d replay-producer
```

**Health.** `bash gx10/scripts/verify.sh` checks the replay or live source, the AnyLog operator, rows arriving in `energy_readings`, `egauge_kafka`, `solar_data` and `nilm_disaggregated` in the last five minutes, 22 heads from inference, the backend, the dashboard, the Remote GUI and a chat round trip to Nemotron. Exit code is the number of failed checks.

**Tests.** `bash gx10/scripts/run_tests.sh` runs the suite inside the training image, or the NeMo AutoModel image if that was not built: 53 passed and 1 skipped on 2026-10-11.

**Training and serving take turns.** Stop `nilm-nemotron` and Ollama before training, and put them back with `deploy_round.sh swap`. The dashboards keep running on the BiLSTM fallback in between.

**Things that bit us.**

| symptom | cause | fix |
|---|---|---|
| resumed rounds train at 1e-5 | AutoModel restores the scheduler and its values win | `override_opt_param_scheduler: true`, `lr_decay_steps: 2000` |
| merge fails to replace `~/nilm/merged` | the merge writes as root in the container | `recurrent_rounds.merge()` swaps it inside the container |
| `Cuda is not available` in the `nilm` container | the container lost its GPU devices after a host systemd reload | `docker restart nilm` |
| `sudo` takes 20 s to a minute | slow on this host | scripts wait for it; give `SUDO_PW` or passwordless `systemctl` |
| unanswered heads on Panel 3 | the model put pairs on one line, comma separated | the parser reads comma and semicolon pairs |
| AnyLog operator serves nothing after a restart | the arm64 node policy script aborts before its local script | the `anylog-init` sidecar reapplies the operator setup |
